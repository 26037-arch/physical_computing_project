# 특히 자랑하고 싶은 기술

각 항목의 수학적 근거(상태 표현, 거리표가 허용적인 이유, OLL/PLL 키 유도, 공식 변환)는 [MATH.md](MATH.md) 에 있다.

## 1. 보드 안에서 도는 CFOP 풀이기 — RAM 2 KB(Uno)에서도 동작
- 큐브 상태를 코너 8개·엣지 12개의 (위치, 방향) 배열 40 바이트로 표현하고, 18가지 회전을 치환표(`MOVE_*`)로 적용한다 ([cube.cpp](../firmware/main/cube.cpp)).
- **탐색 중에는 큐브 전체를 복사하지 않는다.** 크로스 엣지 4개와 지금 끼우는 슬롯의 코너·엣지 등 "관심 조각"의 상태(엣지 `위치*2+방향`, 코너 `위치*3+방향`, 각 1 바이트)만 추적한다. 한 수에 조각당 표 조회 2번(`EDGE_TO/EDGE_DO`)으로 갱신되고 휴리스틱도 그 값으로 바로 조회한다 ([solver.cpp](../firmware/main/solver.cpp) `eStep/cStep`). 추적 배열은 단계당 12 바이트(실제 `search()` 스택 프레임은 약 67 B)라 깊이 14까지도 Uno의 RAM 안에 들어간다. 실측: Uno 빌드 정적 RAM 942 B(45 %), 플래시 27,000 B(83 %); R4 WiFi 플래시 77 KB(29 %), 정적 RAM 9.4 KB(28 %).
- IDA* 가지치기: 같은 면 연속 금지, 반대면 쌍(U/D 등)은 한 순서로만 → 분기 수 18 → 약 13.

## 2. 가지치기 거리표를 PC에서 BFS 로 만들어 플래시에 굽는다
- 크로스: 크로스 엣지 두 개씩 6쌍의 (24×24) 거리표. F2L: 슬롯마다 코너·엣지 쌍 (24×24) 거리표 (D 제외 15수 기준). 휴리스틱은 쌍 거리의 최댓값이라 허용적(admissible)이고, 한 조각 거리표보다 1~2수 더 정확하다.
- 전부 [tools/gen_tables.js](../tools/gen_tables.js) 가 생성해 `tables.h` 에 PROGMEM 으로 넣는다(선언 배열 합계 10,769 B, 공식 수열 포함). 보드는 부팅 시 아무 계산도 하지 않는다.

## 3. OLL 57 · PLL 21 공식표를 "손으로 패턴 입력" 없이 자동 생성하고 전수 검증
- 사람이 쓰는 공식 표기(`r U R' U' r' F R F'`, `M2 U M2 U2 M2 U M2`, `x R' U R' D2 ...`)를 그대로 적어 두면 [cube.js `expandAlg`](../sim/cube.js) 가 wide·슬라이스·전체회전을 **로봇이 돌릴 수 있는 겉면 6면 수열**로 바꾼다 (r = L + x, M = R L' + x' … 전체 회전은 "표기 면 → 실제 모터 면" 표만 바꾼다).
- 각 공식의 **역연산을 풀린 큐브에 적용**해 "이 공식이 푸는 패턴"의 인식 키(OLL: 코너 방향 3진 4자리와 엣지 방향 4비트를 결합한 uint16, PLL: 코너·엣지 위치 각 2비트×4 = 16비트)를 만든다. 생성기는 OLL 216 상태·PLL 288 상태를 전부 돌려 모두 조회되는지 확인하고, 빠진 경우가 있으면 2-look 조합으로 자동 보충한다. 결과: 57 OLL + 21 PLL 전 경우 커버, 보충 0건.
- 공식표의 오타는 "F2L 을 깨는 공식", "어떤 패턴에도 쓰이지 않는 공식(중복)"으로 즉시 잡힌다.

## 4. F2L 어려운 경우를 위한 두 겹 전략 — 최악 노드 340만 → 55만
- 거리표 값이 작은 슬롯부터 깊이 8 이내 탐색. 모두 실패하면(약 0.6 %) 두 조각을 U층으로 **꺼내는 짧은 탐색 → 끼우기 탐색**으로 나눈다. 수는 2~3수 늘지만 깊이 9 탐색의 폭발(약 13배)을 피한다.
- JS 와 C++ 이 같은 순서·같은 규칙이라 결과가 결정적(deterministic)이다.

## 5. JS 풀이기 == 펌웨어 풀이기 — Wokwi 로 글자 단위 교차검증
- 같은 xorshift32 섞기, 같은 탐색 순서. `node tools/gen_wokwi_test.js 1` 이 JS 풀이 결과로 시나리오를 만들고, Wokwi 보드가 `S 1`, `V` 명령에 낸 단계별 출력이 그 문자열과 정확히 일치해야 통과한다 ([tests/solve_seed1.test.yaml](../tests/solve_seed1.test.yaml)).
- 통과 로그(요약): `CROSS (7): U F U D R' L F2` … `TOTAL 50: …` … `SOLVED ok=1 moves=50`. 섞기부터 풀이 실행까지 모두 스테퍼 6개가 실제로 돈다.

## 6. 회전 문자열 "접점 규칙"을 시리얼 프로토콜로 고정
- `S [seed]` / `V` / `M <수열>` / `P` / `R` / `Q 0|1`. 탐색기는 수열 문자열을 내고 모터 제어부는 그것만 받는다. 2단계(스마트큐브)에서 사람이 섞은 회전은 `M` 명령으로 같은 경로로 들어오면 된다.
- JS 3D 시뮬레이터([sim/](../sim/index.html))도 같은 명령·같은 회전 수열·같은 단계 이름을 낸다(시간값과 일부 LCD 표시는 PC 기준). 실물이 없어도 발표에서 단계별 상태를 보여 줄 수 있다.
- 시뮬레이터는 V2 기구의 **헤드 결합·후퇴 전환**(새 축 결합 → 기존 축 해제)까지 재현해, 시드 1 풀이 50수에 축 전환 48회가 필요하다는 것을 숫자로 보여 준다. 이 값이 자동 이송 설계의 목표 속도를 정한다.

## 7. 파라메트릭 CAD → 같은 STL 을 시뮬레이터에
- V1: [cube_robot_parts.py](../fusion/scripts/cube_robot_parts.py)(Fusion 360 API) 의 상수(mm)만 바꾸면 커플러 D컷 공차, 십자 키 공차, 캡 지름이 바뀐다. V2: [build_robot_v2.py](../tools/build_robot_v2.py)(CadQuery) 가 `--cube-mm`, `--gap-mm` 로 57 mm 출력 큐브와 핀 구동 헤드를 다시 생성하고 솔리드 유효성·간섭 표본을 검사한다. 계획서 위험 대책 "소켓 공차를 시험 출력 여러 개로 맞춤"을 상수 한 줄로 돌릴 수 있다.
- V2 헤드 STL 7종과 `parameters.json` 을 base64/JSON 으로 임베드해(`node tools/embed_models.js` → `sim/models.js`) 시뮬레이터가 실제 출력물 형상과 CAD 조립 좌표 그대로 6면 모듈을 보여 준다. CAD 치수를 바꾸면 스크립트 재실행 → 임베드 재실행만으로 시뮬레이터가 따라온다.

## 8. AVR 핫패스 최적화 — 같은 답, 3.3배 빠르게 (Codex 플러그인과 협업)
- Codex에게 "출력·노드 수가 글자 단위로 같아야 한다"는 제약과 Wokwi 측정값(15.6 s)을 주고 [solver.cpp](../firmware/main/solver.cpp) 최적화를 맡겼다. 결과를 Wokwi 교차검증 시나리오로 다시 검증했다: 108,161 노드 **15,613 ms → 4,733 ms**, 출력 동일.
- 바뀐 것: 자식 노드의 휴리스틱을 **부모에서 계산**해 탈락할 자식은 재귀 호출을 생략(`childFits`), 거리표 하나가 남은 깊이를 넘으면 나머지 조각 갱신 생략(조기 탈출), 거리표 행 주소·크로스 쌍 번호를 IDA* 시작 시 1회 계산, 코너 상태의 `/3`·`%3`을 24바이트 표로 대체.
- "같은 답"을 자동으로 확인할 수 있는 테스트가 있었기 때문에 최적화를 안심하고 맡길 수 있었다.

## 9. 모터 제어: 사다리꼴 가감속 + 정착 시간
- [motors.cpp](../firmware/main/motors.cpp): 1400 µs 에서 시작해 스텝마다 60 µs 빨라져 등속(목표 600 µs, 정수 단계 계산상 620 µs), 끝에서 대칭 감속. 90° = 50 스텝(풀스텝), 180° 는 같은 방향 100 스텝, `'` 는 반대 방향 50 스텝. 수 사이 15 ms 정착. 계획서 위험 "모터가 90°를 못 맞춤 → 저속 시작 후 가속"을 코드로 구현.

## 10. 기구 절차도 "JS == 펌웨어" — 뒤집기·지지 전환을 보드와 시뮬레이터가 같은 횟수로
- V4 는 위 헤드가 없어 U 층을 돌리려면 R/L 헤드로 큐브를 180° 뒤집어야 하고, 매 수 앞에서 "새 지지 결합 → 스위치 확인 → 기존 지지 해제 → 잠금 막대 확인" 이 필요하다. 이 절차를 [mechanism.cpp](../firmware/main/mechanism.cpp) 와 [mechanism.js](../sim/mechanism.js) 에 같은 규칙으로 구현했다 (논리 면 → 물리 면 표 `PHYS[orient]`, 흰색 아래 장착으로 U 수는 뒤집기 없이 아래 헤드가 돌림).
- 보드는 가상 모드에서도 절차를 계획해 `SOLVED ok=1 moves=50 flips=4 regrips=45` 처럼 횟수를 내고, `gen_wokwi_test.js` 가 JS 기구 모델의 값으로 이 줄을 기대값에 넣는다. 실제 모드 시나리오(`gen_mechanism_test.js`)는 Wokwi 의 결합 스위치 버튼을 보드 출력에 맞춰 눌러 주고, 스위치를 안 눌러 주면 보드가 그 수를 돌리지 않고 `ABORTED` 하며 모델을 보존하는 것까지 확인한다.
- 중앙축의 역할(큐브 전체 회전 방지)은 **승강 잠금 막대**가 맡는다: 아래에서 중공 D 축을 지나 센터 판의 사각 소켓까지 올라와 코어를 잡고, 뒤집기 때만 내려간다. 이송 유닛 6개는 모두 같은 서보 크랭크(양 끝 사점)와 결합 스위치다 ([HARDWARE_V4.md](HARDWARE_V4.md) 0절).
